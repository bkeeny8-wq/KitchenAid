# Spec review 02 — after the first fix pass

The fix pass reported all 35 findings from review 01 applied. Re-verification
with the same three lenses, plus a by-hand trace of seven fixture cases, found
**17 distinct defects still open** and `readyToImplement: false` again.

Ten were marked REGRESSION: reported in review 01, claimed fixed, still broken.
The most common shape is a half-applied fix — the call site corrected and the
function body left in the old spelling, or a parameter added to two of the
three places that declare it.

## The outcome of this round was a CUT, not a fix

Five of the twelve blocking and regression findings existed only because of
purchase-unit rounding, which Claude added on its own initiative. It failed
review twice — first because no gate could fire for the fixture, then because
nothing in the document ever wrote the pack or equivalence rows the mechanism
reads. More than half the remaining cost of making the spec implementable was
being spent on a feature Brandon never asked for, so it was cut. See the
section in CLAUDE.md before re-adding it.

### 1. [blocking — REGRESSION] §8 `bridges.v1` (ARCHITECTURE.md:7430) + §5.3 `FoodItemResolver` (:6663–6700) + §2.6 `CatalogEntry` (:1319–1395)

**Problem.** BAGUETTE AND GARLIC BOTH FAIL HERE — nothing in the document ever writes `FoodItem.purchasePack*` or inserts a `CountEquivalence` row. `normalizeCountBucketsToPurchaseNoun` opens with `guard let item, let target = item.purchaseCountNoun else { return subtotals }` (:4674) and `purchaseCountNoun` (:1955) is derived solely from `purchasePack`. Trace for case 3: sum → `[count:slice = 12]`; pass A returns at :4674 (purchasePack nil); pass B/C return at the `> 1` gate (:4756); `purchaseQuantity` returns at `guard let pack = item.purchasePack` (:5061). Alternatively add `purchasePack` and `countEquivalences` to `CatalogEntry` and to `build_catalogue.py`'s emitted schema, and have the mint copy them — but then §0.3's "these field names, no others" and §2.6 must change in the same commit.

### 3. [blocking] §4.2 step 4 (:6206) vs §3.7 `MergeKey` (:5118–5126), §2.25 (:3310), §1 manifest (:409)

**Problem.** Step 4 says "Group by `MergeKey(item:dimensionKey:)`", which puts the dimension in the LINE key — so one `FoodItem` requested in two dimensions becomes two `DraftLine`s. That contradicts (a) `MergeKey`'s own comment two lines below its declaration ("clove and head are separate subtotals ON ONE LINE"), (b) §2.25 and the §1 manifest ("One line per `FoodItem` per list"), (c) `DraftLine.requested: [QuantitySubtotal]` being plural, and (d) step 5's "Surviving buckets become `requested` subtotals, one per dimension, N per line". It also makes three functions unreachable on the requested side, because each group handed to `QuantityMath.sum` then contains exactly one `dimensionKey`: pass B (`collapseCountBuckets`, needs clove and head in one array), pass C, and `collapseAcrossDimensions` (returns early unless a volume AND a mass subtotal are both present, :4847). §4.3(b)'s flour case ("One line, two subtotals, status = .needsBridge") and the two-bucket half of §4.3(d)'s garlic case cannot occur. This is structurally the same defect SPEC_REVIEW_01 B5 found on the `have` side and fixed with `bridgeHave`; the requested side was never corrected. Butter (case 1) survives only because both of its lines are volume.

**Fix.** Separate the two keys explicitly in step 4: group lines by `ItemIdentity` alone, and use `dimensionKey` only as the subtotal bucket inside `QuantityMath.sum`. Either rename `MergeKey` to `SubtotalKey` or state in §3.7 that it keys subtotals, never lines. Then re-read §4.3(b) and §4.3(d) against the corrected grouping.

### 4. [blocking] §4.2 step 6 vs §4.3(b) and §2.24 `ShoppingList.needsAttention`

**Problem.** `LineStatus.needsBridge` has no writer. Step 6's status rule assigns only three values — `.haveEnough` when `needed == 0`, `.partiallyHave` when `needed != 0 && didReduce`, `.needed` when `needed != 0 && !didReduce`. Step 5 and `QuantityMath.subtract` insert `.needsBridge` only into `flags`, never into `status`. But §4.3(b) states outright "One line, two subtotals, `status = .needsBridge`", and `ShoppingList.needsAttention` (line 3274) is `orderedLines.filter { $0.status == .needsBridge || $0.status == .unresolvedItem }` — the "Needs attention" block the §1 manifest pins at the top of `ShoppingListDetailView`. A flour line carrying an irreducible volume+mass pair therefore ships as plain `.needed`, and the pinned partition can never contain a bridge line. This is the I8 defect with the sibling case left in: SPEC_REVIEW_01's I8 even asserted that `.needsBridge` "has a writer", which is false.

**Fix.** Add the rule to §4.2 step 6, beside the `.partiallyHave` clause: when `subtract` returns `flags.contains(.needsBridge)`, `status = .needsBridge` (it outranks `.needed` and `.partiallyHave`, because it is the state a tap can fix). Then make §4.3(b)'s `status = .needsBridge` reachable, and say explicitly which of `.needsBridge` / `.partiallyHave` wins when both apply.
