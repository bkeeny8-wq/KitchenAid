## Blocking (8)

### B1. §3.9 `NameNormalizer.swift`

**Problem.** `NameNormalizer` declares two functions with no bodies inside an `enum`. A body is omissible only in a protocol requirement; in an enum/struct/class this is a hard parse error ("expected '{' in body of function declaration"). This is inside §3, which the document's own header declares is "copied verbatim into the codebase", and `matchKey` is called from `CatalogEntry.matchKey`, `CatalogEntry.aliasMatchKeys`, §4.2 step 4 and `FoodItemResolver`, so nothing downstream compiles either. Quote: ```swift enum NameNormalizer { static func matchKey(_ raw: String) -> String /// "NY strip steak" -> "ny-strip-steak". Used for `lineID` and for a recipe file name. static func slug(_ raw: String) -> String } ```

**Fix.** Give both functions real bodies (the doc comment already specifies the algorithm: lowercase, diacritic-fold, strip punctuation/parentheticals, drop trailing prep qualifiers, conservative singularize with the `asparagus/couscous/molasses/greens/hummus` stoplist). If the intent was to defer the implementation, write `static func matchKey(_ raw: String) -> String { fatalError("unimplemented") }` so the file at least parses — but since §3 is the verbatim build contract, write the real one.

### B2. §5.1–§5.4 (`RecipeLoader`, `IngredientCatalog`, `TweakStore`, `FoodItemResolver`, `InventoryLedger`) and §4.1 (`MealScaling`, `RecipeGraph`, `ShoppingListBuilder`)

**Problem.** Every service in these ```swift blocks is written in protocol-declaration syntax inside a concrete `class`/`enum`: computed properties with a `{ get }` accessor requirement and functions with no body. `{ get }` is legal only in a protocol; in a class body it is "expected '{' in body of variable declaration" / "type annotation missing in pattern". Same for the bodiless `static func`s in the §4.1 enums. These are the signatures the rest of the document calls (`loader.recipe(id:)`, `RecipeLoader.all`, `catalog.load()`, `QuantityMath`'s callers, `ShoppingListBuilder.preview`), so the ambiguity is load-bearing, not cosmetic. Quotes: ```swift @Observable final class RecipeLoader { func load() func recipe(id: String) -> Recipe? /// Non-archived, title-sorted. What the library shows. var all: [Recipe] { get } /// Including archived. What a `recipeID` resolves against. var allIncludingArchived: [Recipe] { get } var allTags: [RecipeTag] { get } ``` ```swift var aisleNames: [String] { get } ``` ```swift enum RecipeGraph { ... static func childScale(for line: IngredientLine, subRecipe: Recipe) -> Rational? } ```

**Fix.** Either mark these blocks explicitly as API sketches (change the fence language from `swift` to text, or wrap each in a `protocol` the class conforms to), or convert them to compilable declarations: `var all: [Recipe] { byID.values.filter { !$0.isArchived }.sorted { $0.title < $1.title } }` and give every `func` a body. Pick one and say which, because §0 tells the next reader that these sections go into the codebase as written.

### B3. §3.1 `Rational.swift` — `init(_:_:)`, `multipliedReportingOverflow`, `addingReportingOverflow`

**Problem.** The initializer's `abs(n)` traps when `n == Int.min`, and the comment asserting that cannot happen is wrong — the overflow-checked operators themselves can produce exactly `Int.min` *without reporting overflow*, then hand it straight to this init. `(-2^62) * 2 == -9223372036854775808 == Int.min` and `multipliedReportingOverflow` returns `(Int.min, false)`, so `Rational(num, den)` runs `abs(Int.min)` and crashes. The same init also traps on `-n`/`-d` when `d == Int.min`, which a hand-authored recipe file can supply through `Rational`'s `Codable` — the very path whose own comment promises "A typo in a committed recipe file must degrade, not crash." This defeats the stated purpose of the entire overflow-fallback design ("the alternative is a trap at the shelf"). Quotes: ```swift /// Int.min numerators cannot arise from any input path — every numerator comes from a /// parsed integer or from an overflow-checked operation below — so the `abs` here is safe. init(_ n: Int, _ d: Int = 1) { precondition(d != 0, "Rational denominator must not be zero") var n = n var d = d if d < 0 { n = -n; d = -d } let g = Rational.gcd(abs(n), d) ``` ```swift let (num, o1) = (a.numerator / g1).multipliedReportingOverflow(by: b.numerator / g2) ```

**Fix.** Make the init total instead of asserting it cannot be reached: clamp or reject `Int.min` up front — e.g. `guard n != .min, d != .min else { self.init(0); return }` (or use `magnitude` and build the gcd from `UInt`), and in `addingReportingOverflow`/`multipliedReportingOverflow` treat a `partialValue` of `Int.min` as an overflow (`if o1 || o2 || num == .min { return (.zero, true) }`). Then delete the comment's safety claim, because the reader after you will trust it.

### B4. §3.6 QuantityMath.collapseCountBuckets (lines 4440–4483) vs §0.10 decision 13, §4.3(d), §8.2 req 9, §1 ShoppingListBuilderTests

**Problem.** The fixture's headline purchase-rounding case is unreachable. `collapseCountBuckets` opens with `guard working.filter({ $0.dimensionKey.hasPrefix("count:") }).count > 1 else { return working }`, the pass-1 loop re-checks `guard countKeys.count > 1`, and pass 1 only folds a noun whose target bucket is ALREADY on the line (`countKeys.contains(equals.dimensionKey)`). The fixture produces exactly one count bucket, `count:slice = 12`, and no `count:loaf` bucket, so nothing fires. `purchaseQuantity` then also no-ops because it requires `subtotal.dimensionKey == pack.dimensionKey` and the seeded pack is `1 loaf` (`count:loaf`). The line ships as "12 slices baguette", directly contradicting §4.3(d) ("folds to exactly 1 loaf"), §8.2 requirement 9, decision 13 ("Pass 1 … is what turns the fixture's '12 slices baguette' into '1 baguette'") and the asserted test "The baguette collapsing to 1 loaf".

**Fix.** Separate two operations. (1) Keep the >1-bucket rule only for folding buckets into each other. (2) Add an unconditional normalization pass that applies a `CountEquivalence` toward the item's PURCHASE noun even when it is the only bucket: if `item.purchasePack` (or `CountEquivalence` chain) resolves `slice → 1/12 loaf`, rewrite the `count:slice` subtotal into `count:loaf` before `purchaseQuantity` runs. Alternatively give `purchaseQuantity` the bridge: when `subtotal.dimensionKey != pack.dimensionKey`, walk `item.countEquivalence(forNoun:)` to convert into the pack's noun, and only return unchanged if no chain exists. Then restate §4.3(d) against whichever mechanism is chosen.

### B5. §3.6 QuantityMath.subtract (lines 4591–4625) and §4.2 step 6

**Problem.** There is no code path that bridges the HAVE side across dimensions, so the pantry case breaks. For a 2 tbsp butter requirement with a 4 oz lot: `requested` holds only `volume`, `have` holds only `mass`. `collapseAcrossDimensions` cannot help — it is only called inside `QuantityMath.sum`, and it returns early unless BOTH a volume and a mass subtotal are present in the same array, which never happens when each side is summed independently. `subtract` itself only clamps and flags; it never reads `gramsPerCup`. Result: `toBuy` = the full 2 tbsp (buying butter he has) and `.needsBridge` is flagged by `if onHand == .zero && hasUnmatchedStock` even though the shipped catalogue gives butter `gramsPerCup: 227`. §4.2 step 6 and §10 risk 3 both say the flag is for the case "with no bridge", and §4.3(b) only works because its requested side happened to carry both dimensions.

**Fix.** Add an explicit bridging step to `subtract`, before the per-requirement loop: for every `have` bucket whose `dimensionKey` is absent from `requestedKeys`, attempt conversion into a requested key using `item.gramsPerCup` (volume↔mass) and `item.countEquivalence(forNoun:)` (count↔mass/volume), emitting the `conversionNote` and `.converted`; flag `.needsBridge` only for buckets that remain unconvertible. Then correct the two `flags.insert(.needsBridge)` conditions so a known density never raises the flag, and update §4.2 step 6 to name the bridging step rather than implying it.

### B6. §4.1 ShoppingListBuilder.preview/build (lines 5440–5458) and §4.2 step 6

**Problem.** The documented inventory exclusions and two of the line flags have no mechanism. Step 6 says the builder excludes "lots with `expiresAt < options.now` unless `countExpiredAsAvailable` → flag `.expiredStockIgnored`" and "lots expiring before `range.end + expiringGraceDays` → flag `.expiringBeforeNeed`", but the only inventory input is the closure `inventoryLevel: (FoodItem) -> [QuantitySubtotal]`, which receives no `Options`, no dates and no lots, and returns no flags. So the builder can neither apply the filters nor set those flags, and `LineFlag.expiredStockIgnored` / `.expiringBeforeNeed` have no writer anywhere in the document. Step 6 also filters by LOT expiry while `InventoryLedger.level(of:)` is specified to sum TRANSACTIONS including orphans with `lot == nil` (decision 8), and nothing says how an unassigned transaction's expiry is judged.

**Fix.** Change the closure to `inventoryLevel: (FoodItem, Options) -> (subtotals: [QuantitySubtotal], flags: Set<LineFlag>)` (or pass `asOf`/`graceEnd`/`countExpired` explicitly and return the flag set), and have `InventoryLedger.level(of:in:includeExpired:asOf:)` return the flags it raised. State explicitly in step 6 that transactions with `lot == nil` are never expiry-filtered and always count, and reconcile the lot-filter wording with the transaction-summing rule.

### I2. §3.6 `QuantityMath.collapseCountBuckets` vs §4.3(d) and §8.2 requirement 9

**Problem.** The function returns untouched unless **two or more** count buckets are present, and pass 1 only folds noun A into noun B when a `count:B` bucket is *already on the line*. The fixture's headline v1 case has exactly one count bucket — `count:slice = 12` — and no `count:loaf` bucket, so it returns immediately; even without the early return, `countKeys.contains(equals.dimensionKey)` is false. `purchaseQuantity` cannot rescue it either, because `guard subtotal.dimensionKey == pack.dimensionKey` compares `count:slice` against a `1 loaf` pack and bails. So the line ships as "12 slices baguette", not "1 baguette" — contradicting decision 13, §4.3(d) and §8.2 req 9, which all name this as the reason purchase-unit rounding moved into v1. (The garlic example works, because clove and head are both present.) Quotes: ```swift guard working.filter({ $0.dimensionKey.hasPrefix("count:") }).count > 1 else { return working } ``` ```swift countKeys.contains(equals.dimensionKey), ``` against §4.3(d): "The fixture's `12 slices baguette` with `slice → 1/12 loaf` folds to exactly **1 loaf**".

**Fix.** Let pass 1 fold into a noun that is not yet on the line by creating the target bucket, and drop the `count > 1` gate to `>= 1` (keep the fixed-point cap). Minimally: when `item.countEquivalence(forNoun:)` resolves to another count noun, convert the bucket and insert the target key whether or not it exists. Alternatively, have `purchaseQuantity` follow one `CountEquivalence` hop to reach the pack's dimension key — but then `ShoppingListBuilderTests`' "baguette collapsing to 1 loaf" assertion belongs on that path instead.

### I3. §3.6 `QuantityMath.subtract` and §4.2 step 6

**Problem.** `subtract` takes `item: FoodItem?` but never uses the density to convert anything — the item is read only as `item?.gramsPerCup == nil` for flagging. Matching is purely by `dimensionKey`, so a requirement in one dimension and stock in the other do not cancel *even when the bridge exists*. For a `preferredDimension == .volume` item with `gramsPerCup` set, requested collapses to `volume` while `inventoryLevel` may hand back a `mass` row: `onHand` is `.zero`, the full requirement is bought, and `.needsBridge` is flagged on an item that carries a bridge. Whether this is a real bug depends entirely on `InventoryLedger.level(of:)` running the same collapse passes with the same item, which §5.4 never says. Quotes: ```swift let hasUnmatchedStock = have.contains { !requestedKeys.contains($0.dimensionKey) } if hasUnmatchedStock && item?.gramsPerCup == nil { flags.insert(.needsBridge) } ``` ```swift let onHand = haveByKey[r.dimensionKey] ?? .zero if onHand == .zero && hasUnmatchedStock { flags.insert(.needsBridge) } ```

**Fix.** State in §5.4 that `level(of:)` must return `QuantityMath.sum(_:using: item)` output — same item, same collapse passes — so both sides land on the same keys; or, better, make `subtract` run `collapseCountBuckets`/`collapseAcrossDimensions` on `have` with the passed `item` before building `haveByKey`, and only flag `.needsBridge` when a bucket survives *after* that attempt. Also gate the inner insert on the density being absent, so a known bridge never produces a bridge warning.

## Minor (16)

### M1. §3.1 `Rational.init(approximating:maxDenominator:)`

**Problem.** The numerator convergent is computed before the denominator bound is tested, so the guard is too loose for the `maxDenominator` the overflow fallbacks pass. `h2 ≈ value × k2`, and with `abs(value)` allowed up to 1e15 and `k2` allowed to exceed 10_000 before the break fires, `a * h1 + h0` can reach ~1e19 and trap on `Int64`. This sits on the path `+` and `*` take *to avoid* trapping, so the recovery can crash where the thing it recovers from would not have. Quotes: ```swift guard value.isFinite, abs(value) < 1e15 else { self.init(0); return } ``` ```swift let h2 = a * h1 + h0 let k2 = a * k1 + k0 if k2 > maxDenominator { break } ```

**Fix.** Tie the guard to the denominator bound — `guard value.isFinite, abs(value) < Double(Int.max) / Double(max(1, maxDenominator)) else { self.init(0); return }` — or compute `h2`/`k2` with `multipliedReportingOverflow`/`addingReportingOverflow` and `break` on overflow. `RationalTests` should cover one value near the bound, since this is the branch nothing else exercises.
