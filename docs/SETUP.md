# KitchenAid — setup on your Mac

## Opening the project

```
git clone https://github.com/bkeeny8-wq/KitchenAid.git
cd KitchenAid
open KitchenAid.xcodeproj
```

Build target is **iOS 17.0**, Swift 5, universal (iPhone + iPad). Signing is
pre-set to `DEVELOPMENT_TEAM = HHSFT2GD2H` and bundle id
`com.brandonkeeny.KitchenAid`, matching your CFAL3 setup, so it should sign
without you touching the Signing & Capabilities tab.

## Getting it onto family phones

This app is never going to the App Store. Two routes:

- **Direct install** — plug the phone in, pick it as the run destination, hit
  Run. Free Apple IDs expire the provisioning profile after 7 days; a paid
  developer account (which team `HHSFT2GD2H` implies you have) gives a year.
- **TestFlight internal testing** — archive, upload, add family as internal
  testers. Still unpublished and not App Review'd for internal testers, and it
  avoids re-installing by cable every time a profile lapses. This is the better
  route for other people's phones.

## Claude Code permissions for this repo

The auto-mode classifier in the cloud session would not let me write
`.claude/settings.json` (it counts as modifying Claude's own config). Create it
yourself to stop Claude Code prompting on every build command — same contents as
your CFAL3 repo plus the test-result reader:

```json
{
  "permissions": {
    "allow": [
      "mcp__Claude_Code_iOS_Simulator__control",
      "Bash(xcodebuild *)",
      "Bash(xcrun simctl *)",
      "Bash(xcrun xcresulttool *)",
      "Bash(sips *)",
      "Bash(plutil *)"
    ]
  }
}
```

## The first build — read this before you start fixing things

Every Swift file here was written in a Linux cloud container with **no Apple
toolchain**. Nothing was ever compiled or run before it reached you: that is
**115 files and about 26,000 lines**, plus three test files that have never
compiled either. It went through two full adversarial review passes for compile
correctness, SwiftData legality and iOS 17 API availability, and five checkers
run green — but none of them is a compiler, and the reviews found real defects
the checkers could not see, including four view types that were constructed and
declared nowhere.

So: expect errors. The useful order is

1. **Build the app target.** Not the tests yet — a broken test file produces
   errors that look like app errors and send you down the wrong hole.
2. **Send Claude the whole error list, don't fix them one at a time.** This is
   the single most useful thing you can do. A build error here is rarely alone:
   the same wrong assumption about an API is usually repeated across several
   files, so one list is worth more than one fix. Copy the Issue navigator, or
   `xcodebuild ... 2>&1 | grep -E "error:"`.
3. **Then the test targets.** `KitchenAidTests` is arithmetic — `Rational`,
   the unit ladder, the shopping maths — and is the first thing in this project
   that will tell you whether the numbers are right rather than merely
   plausible. `KitchenAidUITests` taps all five tabs, which is the cheapest
   check that no screen traps when it renders.

### Two failures that will not look like failures

- **An empty recipe library.** `Resources/Recipes` is a folder reference in a
  generated project file, so `subdirectory: "Recipes"` resolving depends on the
  directory being copied into the bundle. Get that wrong and the app launches,
  every screen renders, and the library is just empty.
  `testBundledRecipesReachTheLibrary` exists for exactly this.
- **An empty Plan, Household or Pantry.** Those are filled by
  `KitchenAidSeed.applyIfNeeded`, which runs once per store from the App's
  launch task. If they are empty, that is where to look — not the screens.

### Scanning needs a real device

Receipt and barcode scanning use the camera, so the **simulator cannot run
them** — `DataScannerViewController.isSupported` is false there, and the screen
is written to say so rather than show a black rectangle. Test those on a phone.
The camera usage string is set as a build setting
(`INFOPLIST_KEY_NSCameraUsageDescription`), because `GENERATE_INFOPLIST_FILE` is
on and there is no Info.plist to put it in. **No image is ever stored** — a
frame is read for its text or its barcode and discarded.

### Once you change a build setting in Xcode, Xcode owns the project file

`KitchenAid.xcodeproj` is generated by `scripts/make_xcodeproj.py`, which is how
a month of Swift files became one command instead of two hand-edited entries
each. The moment you change signing, a capability or any setting in Xcode's UI,
re-running that script would discard it. From then on add files in Xcode, or
tell Claude to edit the pbxproj surgically.

Xcode 16 will also offer to convert the per-file entries to a synchronized
folder group. **Take it** — it is the better end state, and it was not used from
the start only because its required keys could not be verified without an Xcode
to try them on. After that the generator is unnecessary.

## What can be checked without a Mac

All of this runs in a cloud session, and all of it passes today:

```bash
python3 -I scripts/check_swift.py      # 7 structural checks over 115 files
python3 -I scripts/check_xcodeproj.py  # every id defined, referenced, built
python3 -I scripts/test_import.py      # the importer, against all 5 documents
python3 -I scripts/test_catalogue.py   # 670 ingredients, no ambiguous lookups
python3 -I scripts/build_catalogue.py  # regenerate ingredients.json
```

`check_swift.py` catches what a missing compiler makes expensive: a `@Model`
absent from the schema array, an unbalanced brace, a CloudKit-illegal attribute,
a type used and declared nowhere, and a screen nothing can reach. It cannot see
a type error, a wrong argument label or an unsatisfied conformance. Nobody
should claim otherwise.
